# Assumptions

| ID | Assumption | Why it matters | Evidence | Status |
| --- | --- | --- | --- | --- |
| A-001 | Automatic build-time or Kernel instrumentation can redirect ordinary function execution without developer-authored patch widgets. | This is the preferred developer experience. | Phase 0B retained unchanged developer files while instrumenting selected ordinary top-level/instance functions and one `StatelessWidget.build`; direct, virtual, and pre-existing tear-off paths reached guards without PatchView or annotations. Selection/build-graph coverage remains bounded. | VERIFIED (BOUNDED SCOPE) |
| A-002 | A useful subset of changed Dart behavior can run through an interpreted, data-driven runtime on both Android and iOS. | It may avoid downloaded native executable code and a toolchain fork. | Current-source Android narrow/broad physical runs and AUVANA-signed iOS narrow/broad USB runs executed business, capability-mediated async, bounded UI/Riverpod, invalid-signature rejection, rollback, and restart persistence. | VERIFIED (BOUNDED SUBSET) |
| A-003 | A Flutter/Dart fork is not required for the initial transparent-dispatch prototype. | Fork maintenance would dominate project cost and Flutter-version sensitivity. | E0 native AOT and E1 physical Android release proofs ran on stock Dart 3.13.0 and Flutter 3.47.0. This verifies the initial prototype only, not production semantics. | VERIFIED (PROTOTYPE) |
| A-004 | Stable function identifiers can survive source transformation, release compilation, and patch generation. | Patch targeting and compatibility depend on stable identity. | Task 13's structured semantic IDs are stable across whitespace, declaration movement, equivalent checkout roots, and exact signature metadata. Renames/library moves intentionally change ID; signature changes retain identity but fail compatibility. Parts and broader declaration kinds remain unsupported. | VERIFIED (BOUNDED NAMED DECLARATIONS) |
| A-005 | Apple and Google policies permit at least some data-driven Dart behavior updates under bounded capabilities. | Platform viability depends on policy, not only technical execution. | Official policy permits some remote content and Google names a VM/interpreter exception, but neither platform resolves custom Dart behavior patches; see `docs/store-policy/`. | UNVERIFIED |
| A-006 | The connected iPhone can install a locally signed release experiment. | Physical iOS validation is required eventually. | Current-source AUVANA-signed Release builds installed on the physical USB iPhone; entitlements contain `CYT7A4VAZ3.dev.hyfens.conformance`, and both narrow and broad receipt sequences passed. | VERIFIED (LOCAL DEVELOPMENT DEVICE) |
| A-007 | Per-function patch lookup overhead can be kept acceptable or restricted to selected boundaries. | Dispatch overhead may be fundamental for instrumented builds. | Task 22's corrected host-AOT run measured stock 2.0103 ns/call and instrumented-unpatched 6.0329 ns/call (+4.0226 ns, 3.0010x), passing the predeclared <=10 ns and <=5x gate. The result is one hot leaf; broad declaration scaling and device workloads remain unmeasured. | VERIFIED (BOUNDED HOST GATE) |
| A-008 | A local filesystem control plane can register and deliver exact signed Patch Format v1 bytes without becoming a runtime trust root. | The first self-hosted slice must not require a database, cloud service, or private signing-key custody. | `packages/control_plane` unit/HTTP tests passed for Ed25519 admission, digest/canonical checks, exact application/release/patch binding, immutable content-addressed storage, promotion, lookup/fetch, and invalid-signature quarantine. | VERIFIED (LOCAL UNIT/HTTP SCOPE) |
| A-009 | Separate hashed control credentials and application/environment-scoped read-only delivery credentials provide a sufficient initial authorization boundary. | Delivery credentials may be extractable from an app and must not mutate or sign. | Control-plane tests reject delivery mutation, bind foreign tenant/resource IDs to not-found, and persist only token hashes; broader threat campaigns remain pending. | VERIFIED (INITIAL SERVICE SCOPE) |
| A-010 | The new CLI `deploy` command completes a real self-hosted Flutter/device deployment with the existing fixture. | Product workflow usefulness depends on registration/upload/promotion, not only service unit tests. | Task 42 ran `tool release` → `tool patch` → `tool deploy` against the authenticated local service; generated iOS and Android Release bootstraps fetched and activated promoted patches on physical devices, with restart/outage retention. | VERIFIED (PHYSICAL IOS + ANDROID FIXTURES) |
| A-011 | The generated release can reference the read-only delivery configuration without leaking the credential into release metadata or relying on a reverse USB tunnel. | Release-time configuration and transport details affect credential safety and physical reproducibility. | Generated iOS and Android `metadata.json` records the delivery credential as `<redacted>`; iOS used USB installation/file retrieval and Android used ADB Wi-Fi while both app→service paths used the Mac private LAN. | VERIFIED (BOUNDED LOCAL RUN) |
